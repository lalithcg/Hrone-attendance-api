# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health` (lines 72–74) | Returns HTTP 200 `{"status": "ok"}` unconditionally without testing if MongoDB is responsive. | Stop MongoDB or configure an unreachable `MONGO_URI`; `GET /health` still returns 200 instead of 503 as required by the OpenAPI contract. | Added `client.admin.command("ping")` inside a `try/except` block; catches `PyMongoError` and raises `HTTPException(503, "Database unavailable")`. |
| 2 | Startup lifecycle (lines 20–28) | Does not create required database indexes at application startup. | Concurrent duplicate creations create duplicate data or unhandled 500s; `explain` queries report `COLLSCAN` across collections. | Implemented FastAPI `lifespan` handler to idempotently create unique index on `employees.emp_code`, unique compound index on `attendance_logs.(emp_code, date)`, and query indexes on startup. |
| 3 | `compute_late_minutes` (lines 33–37) | Grace period logic evaluates `minutes > 10` after integer floor division rather than checking if elapsed time strictly exceeds 10:00 (600 seconds). Also naively replaces hours/minutes on UTC instants without IST conversion. | Shift 09:30 with punch-in at 09:40:01 IST produces 0 late minutes instead of 10 (explicitly violating rule R2). | Converted timestamp to IST, calculated `(punch_in - shift_start).total_seconds()`, and if `> 600` return `int(total_seconds // 60)`, otherwise 0. |
| 4 | `compute_work_hours` (lines 40–41) | Uses Python's built-in `round()`, which applies banker's rounding (round-half-to-even) instead of round-half-up. | Durations with fractional seconds ending in .005 (e.g. 9090s / 3600 = 2.525h) round to 2.52 instead of 2.53 (violating R4). | Used `Decimal` with `ROUND_HALF_UP`: `Decimal(str(seconds / 3600)).quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)`. |
| 5 | `compute_overtime` (lines 44–47) | (1) Does not enforce 30-minute minimum threshold (counts 5 min overtime as 5). (2) Assumes `shift_end` is on the same calendar date, breaking overnight shifts (`shift_end <= shift_start`). | (1) Punch-out at 18:35 for 18:30 shift end returns 5 instead of 0. (2) Overnight shift punch-out compares against a shift end 16 hours in the past. | Calculated proper IST `shift_end` datetime (+1 day if overnight); returned `int(diff // 60)` only when `diff >= 1800` (30 mins), otherwise 0. |
| 6 | `create_employee` (lines 78–85) | Check-then-insert race condition (`find_one` followed by `insert_one`) allows duplicate `emp_code` records or uncaught 500 `DuplicateKeyError` under concurrent requests. | Sending two simultaneous `POST /employees` requests with identical `emp_code` results in duplicate records or unhandled 500 error instead of 409. | Enforced database unique index on `emp_code` and caught `DuplicateKeyError` to return HTTP 409 with `{"detail": "emp_code already exists"}`. |
| 7 | `EmployeeIn` schema (lines 53–60) | Lacks validation for `emp_code` pattern (`^EMP\d{4,6}$`), email format, string lengths, and the requirement that `shift_start != shift_end`. | Submitting `emp_code="BAD"`, invalid emails, or `shift_start == shift_end` returns 201 instead of 422 Validation Error. | Added Pydantic field validators matching OpenAPI `EmployeeCreate` regex/length constraints and a model validator rejecting identical shift start and end. |
| 8 | `create_employee` serialization (line 82) | Sets `created_at` using naive `datetime.now()`, returning an ISO datetime string instead of epoch milliseconds. | Response schema validation fails against `openapi.yaml` `Employee.created_at` (requires int64 epoch milliseconds). | Stored UTC BSON datetime in MongoDB and converted to integer epoch milliseconds in the API response. |
| 9 | `list_employees` pagination (line 93) | Off-by-one pagination bug: `skip = page * page_size`. When `page = 1`, it skips 20 items and omits the first page entirely. | Calling `GET /employees?page=1` returns items 21–40 (or empty list if <= 20 employees exist). | Corrected skip calculation to `skip = (page - 1) * page_size`. |
| 10 | `list_employees` total count (line 94) | `total = db.employees.count_documents({})` counts the whole collection regardless of the `department` query filter. | Calling `GET /employees?department=Engineering` returns only Engineering items but reports `total` of all employees across all departments. | Changed to `total = db.employees.count_documents(q)` to reflect the filtered set (per R10). |
| 11 | `list_employees` sorting (line 95) | Does not sort by `emp_code` ascending as required by OpenAPI contract. | Employees are returned in arbitrary insertion order. | Added `.sort("emp_code", 1)` to the database cursor. |
| 12 | `punch_in` missing employee handling (line 101) | Does not check if employee exists; accessing `emp["shift_start"]` when `emp is None` raises `TypeError` -> unhandled 500. | Calling `POST /attendance/punch-in` with an unknown `emp_code` returns 500 Internal Server Error instead of 404. | Added explicit check: if `emp is None`, raise `HTTPException(404, "Employee not found")`. |
| 13 | `punch_in` concurrency race condition (lines 104–118) | Uses check-then-insert (`find_one` followed by `insert_one`), allowing concurrent duplicate punch-ins for the same date. | Concurrent punch-ins for the same employee and date yield duplicate entries or unhandled 500 errors instead of 409. | Enforced compound unique index on `(emp_code, date)` and caught `DuplicateKeyError` to return HTTP 409. |
| 14 | `punch_in` date calculation & overnight shifts (lines 102–103) | Derives attendance date from local OS date without IST conversion, and ignores overnight shifts where punches before `shift_end` belong to the previous day. | Punching in at 01:00 IST on 2026-07-07 for an overnight shift (22:00–06:00) records date as 2026-07-07 instead of 2026-07-06 (violating R1). | Converted timestamp to IST datetime, checked overnight shift conditions, and assigned date to `(punch_in - 1 day)` if earlier than `shift_end`. |
| 15 | `punch_in` instant truncation (line 102) | Does not truncate timestamps to whole seconds (R1). | Storing `punched_at = 1783312500900` keeps sub-second milliseconds instead of storing truncated `1783312500000`. | Truncated epoch milliseconds via `(punched_at // 1000) * 1000` before calculation and storage. |
| 16 | `punch_in` schema response violation (lines 119–121) | Adds extraneous `"id"` field to returned document, and leaves `punch_in` as a datetime object instead of epoch milliseconds. | Contract schema validation fails because `AttendanceRecord` forbids `id` and requires integer milliseconds for `punch_in`. | Removed `id` field and mapped BSON datetime to integer epoch milliseconds in response. |
| 17 | `PunchInIn` schema validation (lines 63–67) | Accepts invalid `status` values (e.g. `ABSENT`, `LEAVE`) and invalid `punched_at` values (e.g. seconds-looking numbers < 100000000000). | `POST /attendance/punch-in` with `punched_at = 1` or `status = "ABSENT"` succeeds with 201 instead of 422 Validation Error. | Enforced `PresenceStatus` enum (`PRESENT`, `WFH`, `ON_DUTY`) and validated epoch milliseconds range. |
| 18 | `list_attendance` memory exhaustion (lines 144–147) | Loads the entire collection into Python memory (`list(db.attendance_logs.find(q))`) and sorts in Python. Fails on ~100k documents. | At 100k records, the endpoint encounters high latency, excessive memory consumption, or OOM crashes. | Handled sorting and pagination directly in MongoDB using `.sort([("date", -1), ("emp_code", 1)]).skip(skip).limit(page_size)` backed by index. |
| 19 | `list_attendance` date filter validation (lines 127–128) | Does not validate that `date_from <= date_to`. | Querying `date_from=2026-07-10&date_to=2026-07-01` returns 200 with empty list instead of 422. | Added validation returning HTTP 422 when `date_from > date_to`. |

Also note anything you looked at and decided was **not** a defect, and why:
- **Fixed UTC+05:30 offset for IST**: India Standard Time (IST) does not observe Daylight Saving Time (DST) and remains strictly UTC+05:30 throughout the year. Hardcoding `timezone(timedelta(hours=5, minutes=30))` is correct and efficient.
- **Storing dates as `"YYYY-MM-DD"` and shift times as `"HH:MM"`**: Keeping calendar dates and shift times as plain strings avoids artificial timezone attachment and matches the schema described in `DATA_MODEL.md`.
